# Diagnose portless `/api` 502

## Objective & Hypothesis

- Intent class: Reality.
- Mode: Diagnose.
- Objective: explain why `https://partner-up.localhost/api/` returns 502 while the backend dev server appears healthy and Vite has a `/api` proxy configured.
- Working hypothesis: the failure is in the frontend-to-portless proxy path, not necessarily in the backend app process itself.

## Guardrails Touched

- Root `AGENTS.md`: use `pnpm dev:ensure` for local frontend/backend validation.
- Frontend runtime config: `apps/frontend/vite.config.ts`.
- Backend runtime entry/env: `apps/backend/src/index.ts`, `apps/backend/src/lib/env.ts`.
- Portless orchestration: `scripts/ensure-dev-servers.mjs`, `scripts/portless.mjs`, `portless.json`.

## Verification

- Run `pnpm dev:ensure --timeout-seconds=120`.
- Compare HTTP results for:
  - `https://api.partner-up.localhost/health`
  - `https://partner-up.localhost/`
  - `https://partner-up.localhost/api/`
  - local backend port from backend logs/env.

## Current Understanding

- In portless mode, Vite computes `backendProxyTarget` as `https://127.0.0.1`.
- Vite also sends `Host: api.partner-up.localhost` for `/api` proxy requests.
- Backend `.env` has `PORT=4002`; portless may override `PORT` when managing the backend app.
- Current reproduction after `pnpm dev:ensure`:
  - `https://api.partner-up.localhost/health` returns 200.
  - `http://127.0.0.1:4331/health` returns 200.
  - `https://partner-up.localhost/` returns 200.
  - `https://partner-up.localhost/api/` returns 404, not 502.
  - `https://partner-up.localhost/api/meta/build` returns 200 and matches the direct backend route.
- Backend logs confirm `GET /api/` reaches backend and returns 404. `/api/` is not a mounted backend route.
- There are old same-name portless wrapper processes from earlier runs. Current active routes point to the fresh `4006` frontend and `4331` backend targets.
- Recheck for the concrete reported endpoint:
  - `https://partner-up.localhost/api/config/public/home_page_wechat_qr_code` returns 200.
  - `https://api.partner-up.localhost/api/config/public/home_page_wechat_qr_code` returns 200.
  - `http://127.0.0.1:4331/api/config/public/home_page_wechat_qr_code` returns 200.
  - Backend log shows this request entering Hono and returning 200 in 2-8ms.
- `~/.portless/proxy.log` contains the 502-class evidence:
  - `Proxy error for partner-up.localhost: connect ECONNREFUSED 127.0.0.1:4006`
  - `Proxy error for api.partner-up.localhost: connect ECONNREFUSED 127.0.0.1:4331`
- Active `.localhost` routes are stored in `/home/yyh/.portless/routes.json`.
- Older LAN `.local` routes still exist in `/var/lib/portless-mvp-ha/routes.json` and old wrapper processes are still alive, but they are for `partner-up.local` / `api.partner-up.local`, not the active `.localhost` hostnames.

## Next Step

- Likely explanation to report: the 502 HTML is generated by portless when its route registry points at a local target port that is not accepting connections. In this app, the frontend API path has two portless-dependent hops, so `api.partner-up.localhost` being ready does not by itself prove `partner-up.localhost -> Vite -> api.partner-up.localhost -> backend` is ready.
