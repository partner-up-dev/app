# `6-3.1f` Decision Log

| ID | Decision | Exit proof |
| --- | --- | --- |
| `6-3.1f-D1` | A source mutation generates a UUID inside its committing transaction. No source table column or generic event/outbox table is added: the durable generic Job carries `meetingPointUpdateId`, source description and source timestamp. | Two rapid updates with equal clock time have different task keys and payload IDs; a rolled-back UUID has no visible Job. |
| `6-3.1f-D2` | A multi-PR type/POI mutation may share one source-operation UUID, but each changed PR has its own causation `partner_request:<prId>:meeting-point:<uuid>`; recipient identity is added only by Notification's private creation key. | One source operation can fan out over multiple changed PRs without cross-PR coalescing or ambiguous causation. |
| `6-3.1f-D3` | Generic payload retains immutable `meetingPointDescription` and `updatedAtIso`; dispatch rechecks recipient eligibility but never reads the current effective location to rewrite historical event content. | A newer update or participant exit cannot alter the older task's rendered facts; ineligible dispatch skips before I/O. |
| `6-3.1f-D4` | Preserve the existing effective-change detector and no-description suppression rule. A source-only change with equal visible content, or a transition to no usable description, creates no meeting-point notification. | Resolution tests and source scenarios show no task for those cases. |
| `6-3.1f-D5` | Each source owns a named serializable transaction and invokes a narrow transaction-bound Notification port. No generic transaction callback, generic outbox, Opportunity, Delivery or Wave abstraction is introduced. | Injected handoff failures roll back the source row/config/POI and generic Job together. |
| `6-3.1f-D6` | Channel configuration is a Notification dispatch capability, not a prerequisite for committing the source event. Generic work can be scheduled without a provider call; an unconfigured channel produces a classified dispatch refusal. | Source success does not depend on provider configuration; channel unit proves the refusal shape. |
| `6-3.1f-D7` | Generic meeting-point credit is limited and preference-preserving on accepted sends. Known WeChat permission revocation clears preference and credit; ordinary credit exhaustion does not revoke user intent. | Final accepted credit keeps opt-in true; a zero-credit task skips; 43101 clears both. |
| `6-3.1f-D8` | The POI controller returns to protocol-only responsibility by delegating PUT mutation to a POI use case. The old concrete meeting-point handler remains a pending-row drain only. | Controller no longer owns before/after/scheduling logic; static inventory finds no new legacy creation caller. |
| `6-3.1f-D9` | PR-content's named bridge includes PR slot release, capacity validation and status recalculation only when a preflighted time edit requires release. Those writes determine the same source-time active roster as meeting-point fan-out; reminder cancellation/rebuild, promotion, messages and alternative notices stay explicitly post-commit until they receive their own transaction-bound protocols. | An injected handoff failure restores both core content and released slots; successful mixed edit excludes released recipients from generic tasks. |
| `6-3.1f-D10` | A preflighted content-release candidate is released only if its slot is still active under the locked transaction. A stale candidate is skipped, rather than overwriting an exited or otherwise changed slot; post-commit cleanup follows the actual release result. | The repository update predicates on active status and the source bridge returns the actual released slot IDs. |
| `6-3.1f-D11` | PR-type coordination currently changes fields of one immutable type-config key, not the key itself. Its source transaction locks that config first and then every PR of the exact type in ascending ID order; SERIALIZABLE retry arbitrates concurrent content/reclassification writes. One operation UUID is shared across all changed PRs, while PR ID supplies the per-PR causation distinction. | A multi-PR route scenario shows a shared operation UUID/correlation with PR-distinct causation; an injected second handoff failure restores the config and removes every prior generic task. |
| `6-3.1f-D12` | Coordination is event-bearing source behavior, not a generic persistence slice. The neutral PR-type-config command no longer exports a bare coordination write; all current coordination mutations must use the named atomic source port. | Static import inventory finds the admin route delegated only to the source port and no callable bare coordination command. |
| `6-3.1f-D13` | POI rename observes the locked union of exact old and new location names, but it does not invent a removal notification: an old-name PR whose fallback becomes null remains suppressed under the existing no-description rule. POI locks before its affected PRs; real deltas from the same update share one operation UUID. | A rename route scenario shows only new-name visible fallback fan-out and no false old-name removal task; static/source review shows the old/new union lock query. |
| `6-3.1f-D14` | Once all three source families use generic Notification handoff, delete the concrete meeting-point creation API and its source collectors/policy. Retain only startup registration, historical decoder/handler/Delivery accounting, and recipient-prefix cancellation to drain already-pending legacy Jobs. | A static absence search finds no creation symbols or source concrete edges; a manually persisted old Job executes through the registered compatibility handler. |
| `6-3.1f-D15` | A pure cross-domain meeting-point rule imports owner facts from named low-dependency query entrypoints, never an aggregate barrel that can initialize mutation use cases. Initialization order is not an acceptable semantic dependency. | Full backend scenarios cover the formerly cyclic PR-detail path after the POI public-use-case export. |
